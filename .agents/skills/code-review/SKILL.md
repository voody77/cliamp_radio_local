<!-- Adapted from mattpocock/skills (MIT) and Agentic Coding Design Patterns. -->

Ревью идёт по двум независимым осям:

- **Standards** — соблюдены ли стандарты репозитория;
- **Spec** — реализовано ли то, что просили, и нет ли лишнего.

Если в репозитории есть `docs/review.md`, прочитай его и следуй формату.
Если нет — используй процесс ниже.

## 1. Зафиксируй точку

Пользователь называет commit, ветку, тег или merge-base. Если точка не
названа, спроси. Проверь, что ссылка разрешается и diff не пуст.

```bash
git diff <fixed-point>...HEAD
git log <fixed-point>..HEAD --oneline
```

## 2. Standards

Источники: `AGENTS.md`, `CONTRIBUTING.md`, ADR и правила линтеров.

Для каждого замечания укажи файл, фрагмент и нарушенное правило. Базовые
эвристики — только повод присмотреться, а не жёсткий запрет:

- непонятное имя;
- дублирование;
- feature envy;
- data clumps;
- primitive obsession;
- повторяющиеся switch;
- shotgun surgery;
- divergent change;
- преждевременная абстракция;
- цепочки сообщений;
- middle man;
- refused bequest.

Стандарт репозитория важнее эвристики. Не повторяй то, что уже ловят
линтеры и CI.

## 3. Spec

Найди источник требований: issue/PR в коммитах, путь от пользователя,
`docs/`, `specs/` или PRD. Если источника нет, явно напиши
«спецификация не предоставлена» и пропусти ось Spec.

Проверь:

- что не реализовано или реализовано частично;
- что добавлено сверх задачи;
- что выглядит реализованным, но противоречит спецификации.

Цитируй требование и место в diff.

## 4. Отчёт

```text
## Standards
- <файл>: <нарушение>; <почему>

## Spec
- <требование>: <что не сделано или сделано неверно>

Итог: Standards — <N>; Spec — <M>.
```

Не смешивай оси и не выбирай «победителя». Если инструмент поддерживает
субагентов, запусти две проверки параллельно; иначе выполни их
последовательно.

Ревью не правит код: сначала отчёт, потом отдельное изменение.
