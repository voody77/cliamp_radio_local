# Упрощение кода

Цель — сделать код проще, не меняя поведение. Это рефакторинг, а не
переписывание задачи.

## 1. Сначала понять

- Зачем этот код существует? Кто его вызывает?
- Есть ли тесты, фиксирующие поведение?
- Есть ли внешние контракты: API, формат файла, БД, события?
- Не является ли «странность» осознанным обходом? Смотрите ADR и
  `known-issues`.

Не удаляйте код только потому, что он кажется неиспользуемым: проверьте
ссылки, историю и тесты.

## 2. Что упрощать

- глубокую вложенность — ранними возвратами и выделением функций;
- дублирование — общим helper или модулем;
- длинные функции — шагами с понятными именами;
- неясные имена — доменными терминами из `docs/glossary.md`;
- лишние абстракции — удалением, если нет второго применения;
- большие diff — разделением на независимые изменения.

## 3. Правила

- Один шаг — одно изменение; после каждого шага тесты зелёные.
- Не меняйте публичный контракт без ADR и миграции.
- Не оптимизируйте скорость за счёт читаемости без измерения.
- Не добавляйте «на будущее» параметры и слои.
- Не смешивайте упрощение с исправлением бага: сначала баг, потом
  рефакторинг.

## 4. Проверка

- тесты до и после;
- diff стал меньше или понятнее;
- нет новых `TODO` и мёртвого кода;
- `python3 scripts/check_docs.py`;
- в отчёте: что упрощено, что сознательно оставлено и почему.
