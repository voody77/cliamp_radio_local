# AGENTS.md

Точка входа для разработчиков и их агентов. Читайте первым; конкретные
процедуры — по ссылкам из маршрутизатора задач. Документация ведётся
**на русском языке**.

## 0. Рабочие правила

Эти правила обязательны для человека и агента. Если правило конфликтует с
задачей — сначала спросите, не обходите его молча.

### 0.1. Качество и чистота

- Код, конфиги, миграции и документация должны быть понятными, надёжными,
  безопасными и поддерживаемыми.
- Один источник истины. Не дублируйте константы, форматирование, проверки,
  стили, SQL и тексты. Общее выносите в существующий helper или документ.
- Ошибки обрабатывайте явно: не глотайте исключения, не подменяйте один код
  ошибки другим, не оставляйте пустой `catch`.
- Исправляйте причину, а не симптом.
- Секреты не логируются и не попадают в ответы, ошибки и документацию.
- Любое отклонение (временный обход, дубль, legacy-путь) фиксируется в коде
  или `docs/known-issues.md` с условием закрытия.

### 0.2. Тесты как доказательство

- Тест отвечает на вопрос: «работает ли это, не сломается ли, безопасно ли и
  достаточно ли быстро?» — а не просто увеличивает coverage.
- Для изменения добавляйте успешный сценарий, отказ, граничный случай и,
  если был дефект, регрессионный тест.
- Контракты, права и безопасность проверяются отдельно; тяжёлые операции —
  замером или профилированием.
- Тест без утверждения и тест «всё вернулось» без проверки содержимого
  считаются недоказанными.
- Тесты проверяют поведение через публичные швы, а не внутренние детали.
- Пишите вертикальными срезами: один падающий тест → минимальная
  реализация → повтор; не пишите все тесты заранее.
- Ожидаемое значение берите из независимого источника; утверждение не
  должно повторять формулу кода.
- Падающий или нестабильный тест — блокер.

### 0.3. План → утверждение → реализация → ревью → тесты

- Перед нетривиальным изменением составьте план: что меняется, какие файлы и
  контракты затронуты, какие риски и проверки.
- Держите изменение в границах задачи; попутные находки выносите в
  отдельную задачу, а не в текущий diff.
- **Не начинайте реализацию до явного утверждения плана пользователем.**
  Тривиальную правку можно обозначить и сделать сразу.
- После реализации проведите ревью собственного diff: нет ли дублей, лишних
  изменений, секретов, сломанных ссылок и необновлённых доков.
- Затем добавьте или обновите тесты и прогоните проверки из раздела 4.
- В отчёте отделяйте проверенное на живом стенде от непроверенного.

### 0.4. Зрелые решения вместо самописа

- Сначала ищите поддерживаемую библиотеку, фреймворк или штатный механизм.
- Не пишите сами парсеры, аутентификацию, криптографию, работу с датами,
  retry, кеш, HTTP-клиент, валидацию и миграции, если есть зрелое решение.
- Проверяйте лицензию, поддержку, безопасность и совместимость версий.
- Выбирайте простейшее решение, закрывающее текущие требования; не
  добавляйте абстракции и совместимость «на будущее» без контракта.
- Свой код допустим, когда готовое решение не подходит по контракту,
  лицензии или весу; причину зафиксируйте в ADR или комментарии.

### 0.5. Не фантазировать

- Не выдумывайте имена полей, API, таблиц, чисел и поведение. Проверяйте по
  репозиторию, схеме, тестам, документации проекта или upstream-источникам;
  память модели — только гипотеза.
- Если кейс непонятен, противоречив или требует доступа/решения владельца,
  остановитесь и задайте вопрос.
- Явно отделяйте факты от допущений. Допущение, меняющее поведение,
  фиксируйте в плане и документации.
- Не подгоняйте данные и проверки под желаемый результат.

### 0.6. Актуальный контекст

- Изменили поведение — обновите `AGENTS.md`, `docs/architecture.md`,
  профильный документ и `docs/README.md`.
- Новое ограничение — в `docs/known-issues.md`.
- Архитектурное решение — ADR в `docs/decisions/`.
- Изменение для пользователя — в `CHANGELOG.md`.
- Документация считается частью «готово»: устаревший док — такой же дефект,
  как падающий тест.

## 2. Границы и запреты

- Не добавляйте в репозиторий секреты, реальные пароли и ключи.
- Не отключайте проверки и не обходите контракты ради «быстрого» результата.
- Не дублируйте документацию: ссылка лучше копии.
- Не редактируйте генерируемые файлы руками.
- Исторические документы не являются источником истины.

- Скрипт идемпотентен или явно документирует обратное.
- Секреты приходят из окружения, а не из аргументов и логов.
- Ошибки возвращают понятный exit code.
- Повторный запуск не дублирует результат.
- Внешний контракт зафиксирован и проверяется.
- Retry, таймауты и rate limits описаны.
- Секреты и подписи не попадают в логи.
- Недоступность внешнего сервиса деградирует предсказуемо.

## 3. Быстрый старт

```bash
# Установка
make install

# Тесты
make compile

# Линтер
make compile

# Сборка
make all
```

Если команда ещё не настроена, замените `TODO` в `AGENTS.md` и
`agent-context.json` до первого релиза.

## 4. Проверки

```bash
make compile
make compile
python3 scripts/check_docs.py
```

Для релиза:

```bash
python3 scripts/check_docs.py --strict
```

`--strict` дополнительно валит незаполненные `TODO` и устаревший
`docs/status.md`.

## 6. Инварианты

- Один источник истины для версий, конфигов и документации.
- Секреты — только в окружении или хранилище секретов.
- Ошибки обрабатываются явно и не маскируются.
- Новое поведение покрыто тестами, включая отказ и границу.
- Публичные контракты описаны в `docs/` и проверяются.
- История изменений — в `CHANGELOG.md`.

## 7. Язык документации

Вся документация — на русском. Английский допустим только для кода, команд,
путей, env-переменных, API, UI-меток и аббревиатур.

| Оставляем как есть | Переводим |
|---|---|
| код, SQL, команды, пути | обычный текст и заголовки |
| имена полей, сервисов, env | `production` → «промышленная эксплуатация» |
| аббревиатуры (`API`, `SQL`, `CI`) | `live` → «живой стенд» |
| машинные значения и коды | `read-only` → «только чтение» |

Устоявшиеся заимствования (`bootstrap`, `seed`, `fallback`, `allowlist`,
`draft`, `pack`, `scope`) допустимы, если русский эквивалент неуклюж.

## 8. Известные ограничения

Текущее состояние — в [`docs/status.md`](docs/status.md), блокеры — в
[`docs/known-issues.md`](docs/known-issues.md). Не обходите их в коде и
конфигах: у каждого пункта есть владелец и условие закрытия.

## 9. Карта репозитория

```text
docs/           документация (вход — docs/README.md)
scripts/        проверки и обслуживание
```

Дополните карту реальными каталогами проекта.

## 10. Определение готовности

1. Тесты и линтеры зелёные.
2. `python3 scripts/check_docs.py` проходит.
3. Обновлены `docs/status.md`, `CHANGELOG.md` и профильные документы.
4. Секреты не попали в git, логи и ответы.
5. В отчёте указано, что проверено на живом стенде, а что нет.
